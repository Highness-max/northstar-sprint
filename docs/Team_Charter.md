## GitHub Workflow

### Branch Naming

Each member works on their own branch.

Examples:

- feature/dashboard-ui
- feature/order-status
- feature/returns
- docs/team-charter
- feature/testing

No one should develop directly on the `main` branch.

### Pull Requests

- Complete work on your branch.
- Open a Pull Request.
- Another teammate reviews before merging.
- Merge into `main` after approval.

---

## Commit Message Convention

Every commit should follow this format:

`<type>: <what changed> - <why it matters>`

Good examples:

- feat: add order lookup - reduces support tickets
- docs: create team charter - defines collaboration rules
- fix: clear button reset - improves user experience

Not allowed:

- wip
- updates
- final

---

## Task Management

We will use the GitHub Project Board.

Tasks move through these stages:

- Backlog
- To Do
- In Progress
- Review
- Done

Board status should be updated on the same day work is completed.

---

## Definition of Done

A task is considered complete only when:

- The assigned work is finished.
- It has been tested.
- Changes are committed with a proper commit message.
- The board is updated.
- If applicable, the Pull Request has been merged.

---

## Conflict Resolution

If a disagreement occurs:

1. Discuss respectfully.
2. Focus on the project requirements.
3. If unresolved, involve the Team Lead.
4. Use majority agreement if necessary.

---

## Escalation Process

If a member shows no visible GitHub or Project Board activity for two consecutive days:

1. Contact them through WhatsApp.
2. Confirm whether they need assistance.
3. Redistribute urgent work if necessary.

---

## Team Commitment

We agree to:

- Communicate clearly.
- Complete assigned tasks on time.
- Use meaningful GitHub commits.
- Keep the Project Board updated.
- Support one another to deliver a successful MVP.
